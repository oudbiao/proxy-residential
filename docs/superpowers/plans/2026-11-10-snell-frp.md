# Snell ShadowTLS multi-VPS deployment implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking.

**Goal:** One Japanese Mac Docker container connects independently to three VPS relays; Surge manually chooses a Snell + ShadowTLS node.

**Architecture:** Each VPS runs frps with an independently generated private CA and token. A single Japanese container runs one sing-box process with separate Snell/ShadowTLS inbounds per VPS and one reconnecting frpc process per VPS. VPS_N environment variables hold generated proxyjp:// connection strings.

**Tech Stack:** Python standard library (3.9+ host, 3.13 container), OpenSSL, frp 0.72.0, sing-box 1.14.4, Docker Compose, launchd.

**Spec:** docs/superpowers/specs/2026-11-10-proxy-jp-design.md

## Global Constraints

- Surge Snell version=4, ShadowTLS version=3; sing-box Snell inbound version=5 implements its v4 wire protocol.
- Default proxy TCP 8443, tunnel TCP 7000, ShadowTLS handshake www.cloudflare.com:443; initialization can override.
- Japan one container, VPS_1/VPS_2/VPS_3 in Compose; independent credentials and frpc for every nonempty numbered variable.
- No public Japan ports, host networking, privileged mode, Docker socket, or TUN.
- Force and verify frp TLS; restrict frps allowed ports; no VPS direct fallback.
- Generated secrets excluded from Git, directories 0700, sensitive files 0600; initialization refuses existing output.
- No real remote deployment or shared-branch push without device information/user instruction.
